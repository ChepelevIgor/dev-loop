# Dev Loop: подробная справка

Dev Loop помогает превратить макеты в понятные задачи для разработчиков, а затем проверить изменения в приложении и коде. Навык — отдельное действие плагина, которое можно вызвать по имени или попросить обычными словами.

## start

**С чего начать**

Открой проект, над которым работаешь. Передай номер Linear, описание задачи, номер PR или макеты — в зависимости от команды.

| Хочу | Навык | Пример запроса |
|---|---|---|
| Выполнить задачу | `start-task` | `start-task T-10` или `start-task Добавь сохранение имени` |
| Проверить задачу до и после | `sim-verify-task` | `sim-verify-task T-10`, `sim-verify-task Проверь сохранение имени` или `sim-verify-task PR 2` |
| Проверить PR, разобрать замечания, ответить и закрыть все треды | `close-threads` | `close-threads PR 2` |
| Проверить макеты, подготовить по ним задачи или перенести макет в код проекта дизайна | `filter-design` | «Вот макеты регистрации. Подготовь по ним задачи», «Проверь этот макет по правилам нашего проекта» или «Собери этот макет в репозитории дизайна» |
| Понять, баг это или нет, и насколько бизнес-логика задачи сходится с мобилкой | `check-bug` | `check-bug TASK-12` или `check-bug После перезапуска сбрасывается имя` |
| Сверить мобилку с текущим дизайном в workbench по скриншоту экрана или его части — вид и бизнес-логику | `match-design` | «Сверь этот скрин с дизайном» и приложить скриншот |
| Разобрать спорный вопрос: что выбрать и почему | `debate` | «Устрой спор: оставить онбординг из 3 экранов или сократить до одного?» |
| Понять, что выбрать и как пользоваться | `help` | «Объясни Dev Loop и покажи пример работы с макетами» |

В Codex выбери навык в меню или вызови его через `$`, например `$sim-verify-task PR 2`. Если меню показывает префикс плагина, выбери соответствующий пункт Dev Loop. В Claude Code команды плагина имеют вид `/dev-loop:close-threads PR 2` и `/dev-loop:help`. В обычном сообщении достаточно назвать Dev Loop и желаемое действие.

Номер PR относится к текущему проекту. Чтобы выбрать PR другого проекта, передай полную ссылку. Формы `PR 2`, `pr 2`, `#2` и `2` подходят для команд, принимающих PR. Номер Linear указывается с буквенным префиксом, например `T-10`. Для описания задачи доступ к Linear не нужен.

## workflow

**Как устроена работа**

Есть два основных пути. Можно пройти нужный путь целиком или выбрать один навык.

**От макета к задачам:**

1. Ты передаёшь HTML-макеты, папку с вариантами или доступную ссылку на артефакт.
2. Плагин определяет экраны и делает снимки макетов. При полной настройке показывает рядом текущие экраны из проекта дизайна.
3. Проверяет правила оформления, доступные возможности сервера и существующие экраны приложения.
4. Предлагает разбиение на задачи. Варианты одного экрана остаются в одной задаче; изменения приложения и сервера разделяются.
5. Открывает страницу, где можно выбрать вариант, попросить доработку или пропустить макет.
6. По запросу на создание задач отправляет выбранное в Linear со скриншотами и страницей. Если указана существующая задача, добавляет материал к ней.

**От задачи к проверенному результату:**

1. Ты указываешь номер Linear или описываешь изменение.
2. **Бизнес-ревью:** какую метрику двигает задача, что меняется для пользователя простыми словами, Definition of Done и сценарии Given / When / Then. Если не хватает картинок, данных или продуктового решения, это подсвечивается. Если без ответа работать нельзя, задача останавливается и ждёт тебя.
3. **Техническое решение:** агент описывает, что и где меняется, как это будет проверено.
4. **Тест-кейсы QA:** отдельный проверяющий (Codex) пишет сценарии, по которым будет проверять каждое условие.
5. **Код:** агент делает задачу в отдельной ветке и запускает проверки.
6. **Ревью задачи без PR:** отдельный проверяющий смотрит изменения; подтверждённые замечания исправляются.
7. **Было / стало на симуляторе:** сценарии прогоняются на версии до и после, страница с результатом открывается в браузере.
8. На странице кнопка **Dev Loop**: пишешь комментарий и нажимаешь — работа идёт ещё раз с учётом комментария или продолжается после твоего ответа. PR создаётся, только когда ты его попросишь.

В полном цикле предусмотрено не более трёх раундов исправлений. Если проверка недоступна или остаётся нерешённая проблема, отчёт объясняет, что мешает завершению. Статус «готово» требует подтверждённых проверок.

Плагин работает вместе с агентом в чате. Установка не запускает постоянного помощника в фоне. Кнопка на странице передаёт запрос; для продолжения нужен работающий агент или новое сообщение в исходном чате.

## start-task

**Выполнить задачу**

Когда выбирать: нужно внести изменение, исправить ошибку или продолжить сохранённую задачу.

Есть два варианта:

- `start-task T-10` — прочитать задачу T-10 в Linear и выполнить её.
- `start-task Добавь сохранение имени после перезапуска; пустое имя сохранять нельзя` — выполнить задачу прямо по описанию.

По номеру агент получает описание и условия из Linear. Для текста сохраняет локальную задачу; создавать карточку Linear не нужно. Если уже есть ветка или PR, можно указать их дополнительно.

Навык связывает этапы в один процесс: бизнес-ревью → техническое решение → тест-кейсы QA (Codex) → код → ревью задачи без PR → было / стало на симуляторе. Он сохраняет ход работы, поэтому после перерыва не нужно начинать заново. Для сравнения на симуляторе использует `sim-verify-task`, для ревью — проверяющего из `close-threads`; PR и ответы в треды — только по запросу.

Если на бизнес-ревью не хватает решения (например, не ясно, какую метрику двигаем или для какого тарифа фича), задача останавливается, а вопросы видны на странице. Ответь в поле комментария и нажми **Dev Loop** — работа продолжится с этого места.

Результат: ветка с изменениями, бизнес-ревью, техническое решение, тест-кейсы, результаты ревью и страница было / стало, открытая в браузере. PR публикуется, когда это входит в запрос. Отдельная просьба посмотреть код не означает запуск всего цикла.

Примеры: `start-task T-10`; `start-task Исправь ошибку входа и добавь тесты`; «Продолжи сохранённую задачу APP-42 и покажи, что осталось проверить».

## sim-verify-task

**Проверить задачу до и после**

Можно передать:

- **Номер Linear:** `sim-verify-task T-10`. Несколько задач: `sim-verify-task T-10 T-11`.
- **Описание:** `sim-verify-task Проверь, что имя сохраняется после перезапуска`.
- **PR:** `sim-verify-task PR 2` или ссылку на PR.

Агент берёт условия из указанной задачи, твоего описания или описания PR, находит соответствующие изменения и проверяет нужный результат. Если для задачи Linear нет ключа, сначала пробует MCP в Claude и при необходимости помогает пройти вход в браузере. Для описания или PR подключение Linear необязательно.

Для каждой задачи работа идёт так:

1. Прочитать задачу, описание или PR и составить список конкретных проверок.
2. Найти версию до изменений и версию, в которой задача реализована.
3. Выполнить один и тот же сценарий на обеих версиях с одинаковыми данными.
4. Показать скриншоты до и после для экранов, результаты тестов и ошибки.
5. Сохранить отдельный отчёт с номером задачи и вердиктом по каждому условию.

Например, T-10 требует сохранить имя в профиле. Проверка покажет, как сохранение работало до исправления, сохраняется ли имя после него и остаётся ли оно после перезапуска. При запросе T-10 и T-11 будут два отчёта; условия задач не смешиваются.

Для iOS или Android нужен доступный симулятор/эмулятор и способ собрать обе версии приложения. Если задача затрагивает только серверную логику, проверяются соответствующие операции и тесты; скриншоты там могут быть неприменимы. Полный цикл мобильного Dev Loop по-прежнему требует предусмотренных им изображений.

Если задача ещё не реализована, можно проверить и сохранить состояние «до»; результата «после» пока нет. Если старую версию нельзя запустить или неясно, какая ветка относится к задаче, агент скажет, чего не хватает. Один и тот же изменённый экран не выдаётся за сравнение двух версий.

Для PR сравниваются его реальные версии до и после. Если задача задана текстом, агент использует относящиеся к ней изменения текущего проекта; при неясной связи уточнит нужную ветку или версию. Отсутствующие условия не придумываются по коду.

Результат: отдельный отчёт с условиями задачи, сравнением и выводом. Для T-10 это `.devloop/tasks/T-10/report.html`; для описания или PR создаётся локальный идентификатор и своя страница. Ревью кода PR и закрытие замечаний — команда `close-threads PR 2`.

## close-threads

**Закрыть все треды**

Пример: `close-threads PR 2`. Также подходят `close-threads 2`, ссылка на PR или конкретное замечание текстом.

Один навык доводит PR до состояния «нет открытых тредов». PR — предложение изменить код на GitHub; тред — обсуждение замечания к строке кода.

1. **Ревью.** Отдельный проверяющий (например, Codex CLI) ищет ошибки в логике, необработанные случаи и пробелы в тестах. Если просишь только разобрать уже оставленные замечания, этот шаг пропускается.
2. **Сбор.** Агент собирает все треды и комментарии PR вместе с найденным при ревью.
3. **Решение по каждому треду.** Подтверждённую проблему агент исправляет, проверяет тестами, коммитит и отправляет в ветку PR. Спорное замечание разбирается навыком `debate`: несколько ролей (архитектор, QA, дизайнер, производительность, безопасность и другие) спорят с доказательствами. Ложное срабатывание отклоняется с объяснением.
4. **Ответ и закрытие.** Как только по треду есть решение, агент сразу пишет в него ответ — что сделано (коммит, тест) или почему замечание отклонено — и закрывает тред.
5. **Повтор.** После исправлений агент снова проверяет новый код и собирает треды, пока открытых не останется (не больше трёх кругов).

Вызов навыка — это и есть разрешение отвечать в треды этого PR и закрывать их. Сам PR агент не сливает, не закрывает и не одобряет; в `main` не отправляет. Треды, где нужно твоё решение (ничья в обсуждении, вопрос о продукте, нет доступа), остаются открытыми с вопросом в ответе.

Например, PR №2 добавляет сохранение имени, но код не обрабатывает отказ сервера. `close-threads PR 2` найдёт это, исправит, ответит в треде ссылкой на коммит и закроет его. `sim-verify-task PR 2` проверяет поведение до и после по сценариям; эти команды дополняют друг друга.

Результат: список закрытых тредов (исправлено / отклонено, со ссылками на ответы), оставшиеся открытыми и почему, отправленные коммиты. Наличие отдельного проверяющего указывается честно; без него независимое ревью не считается завершённым. Если проверяющего или доступа к GitHub нет, агент так и скажет и не будет делать вид, что треды закрыты.

## filter-design

**Фильтр дизайна**

Когда выбирать: дизайнер подготовил макеты, и нужно понять, что в них нового и чего не хватает, передать разработчикам понятные задачи или перенести согласованный макет в код проекта дизайна. Это один навык; агент выбирает нужную часть по запросу.

Передай HTML-файлы, папку с вариантами или ссылку на доступный артефакт. Если известны экраны и задача Linear, укажи их. Другой формат сначала нужно привести к доступному для просмотра представлению; плагин не обещает прямой импорт любого редактора.

### Страница сравнения и кнопки

Достаточно сказать «проверь с дизайном» или «запушь это в дизайн». В обоих случаях плагин сначала строит одну страницу сравнения, а дальше решаешь ты кнопками.

Каждый макет получает обозначение D1, D2 и так далее. Плагин показывает его рядом с текущим экраном из проекта дизайна, проверяет и готовит план задач. Текущий экран здесь — представление в репозитории дизайна; для проверки работающего мобильного приложения есть `sim-verify-task`.

**Условия макета.** Для каждого макета агент записывает, при каких данных он нарисован: «новый пользователь, истории сканов нет», «три скана в истории», «ошибка загрузки». Текущий экран снимается при тех же условиях, если проект дизайна умеет их показать; иначе страница предупреждает, что часть отличий — это данные, а не дизайн. Два макета одного экрана с разными условиями — это состояния экрана (нужны оба), с одинаковыми — варианты (выбирается один). Если условие не указано или нарисовано только одно из очевидных состояний (есть история, но нет пустого), это попадает в открытые вопросы задачи, а в бизнес-кейсах «Дано» всегда называет условие.

**Pixel perfect.** На карточке макета переключатель: «Рядом», «Наложение» (макет поверх текущего экрана с ползунком прозрачности), «Разница» (одинаковые пиксели чёрные, всё отличие светится) и «Изменения» (изменённые пиксели красным, рамки вокруг изменённых областей и доля изменённого экрана).

Для каждой задачи плагин ищет в Linear похожие открытые задачи. Агент проверяет, что это та же работа, и предлагает её; если подходящей нет — «новая задача». Выбор можно поменять на странице.

На странице выбери «Взять», «Доработать» или «Пропустить» для каждого макета и куда идёт каждая задача. Дальше:

- **Create Linear tasks** — только задачи: новые создаются с изображениями, в выбранные существующие макеты добавляются комментарием. Страница прикладывается к задаче.
- **Push to design** — то же самое, и сразу перенос: агент собирает каждый выбранный макет в коде репозитория дизайна на отдельной ветке, делает сравнение до и после, запускает проверки и открывает PR. Ссылка на PR появляется на странице и в задаче Linear, так что разработчик может её подобрать. Код, собранный агентом, проверяется в PR; в `main` ничего не отправляется, статус задачи не меняется. Если у одного экрана выбрано несколько вариантов с одинаковым условием, кнопка попросит оставить один; разные состояния экрана переносятся вместе.

Тексты задач следуют шаблонам команды; язык задачи может отличаться от языка чата.

Если задача указана тобой, материал добавляется к ней. Повтор после сбоя вложения продолжает начатую публикацию. После изменения макета, снимков или результатов проверок нужна обновлённая страница и актуальное решение.

Результат: страница выбора, план и, после отправки, ссылки на задачи Linear. Исходные файлы макетов сохраняются; работа идёт с копиями.

### Проверка макета

Проверку можно попросить и отдельно, без страницы и задач. Она охватывает три части:

- **Правила дизайна:** цвета, шрифты, размер текста, отступы и скругления сравниваются с темой проекта. «Токены» — сохранённые значения этих правил, например основной цвет или стандартный отступ.
- **Сервер:** по доступному описанию API проверяется наличие нужных операций и полей. API — способ, которым приложение получает и отправляет данные. Наличие записи в схеме ещё не означает проверку работы функции на реальных данных.
- **Приложение:** поиск существующего экрана и похожих компонентов в мобильном проекте. Это проверка исходного кода; запуск пользовательского сценария выполняет `sim-verify-task`.

Результат: понятный список несоответствий и недостающих возможностей со ссылками на источники. Если какая-то часть недоступна, она помечается «не проверено». Сама проверка не создаёт задачи Linear.

### Перенос макета в код проекта дизайна

Так работает кнопка Push to design; только в полной настройке репозитория дизайна. Навык готовит отдельную рабочую копию и ветку, собирает экран по правилам проекта, делает сравнение до и после, запускает проверки, публикует ветку и создаёт либо использует существующий PR. Этот путь не переносит экран автоматически в мобильное приложение.

Примеры: «Используй filter-design для этих трёх вариантов регистрации. Покажи план перед отправкой в Linear»; «Проверь этот макет через filter-design»; «Есть ли на сервере нужные поля для этого экрана?»; «Перенеси выбранный вариант в проект дизайна и подготовь сравнение». Для публикации: «Отправь этот вариант в репозиторий дизайна и создай PR».

## debate

**Спор**

Пример: «Устрой спор: показывать пейволл сразу после онбординга или после первого скана?» или «debate: 3 спорщика, 1 раунд, коротко — оставить тёмную тему по умолчанию?»

Когда выбирать: есть настоящий выбор с плюсами и минусами, и на него нельзя ответить одной проверкой. Тема любая: продукт, дизайн, архитектура, текст, стратегия. Факт («есть ли поле в API», «падает ли тест») не спорят, а проверяют.

1. **Вопрос и бриф.** Агент формулирует один точный вопрос, варианты A/B/C и бриф: цель, ограничения, что уже решено. Сначала собираются доказательства: файлы, данные, скриншоты, ссылки.
2. **Роли под тему.** Агент сам придумывает роли для этой темы: кто здесь заинтересован или смотрит иначе. Для пейволла это, например, владелец продукта, новый пользователь, платящий пользователь, маркетолог роста и ревьюер магазина приложений. Взгляды ролей должны где-то расходиться; скептик добавляется почти всегда. Готовые роли из библиотеки (продукт, бизнес, пользователь, дизайнер, архитектор, QA, производительность, безопасность) берутся, когда подходят как есть, — обычно в ревью кода.
3. **Раунды.** каждая роль утверждает, возражает, поддерживает или задаёт вопрос, с уверенностью и доказательствами, и оценивает варианты. Утверждение без доказательств не может быть уверенным. Скрипт считает, какие утверждения выдержали возражения и какой вариант лидирует.
4. **Независимый судья.** Вердикт пишет не тот, кто готовил спор, а отдельный агент, который не видел подготовки и не участвовал: он получает только бриф, вопрос, реплики ролей и подсчёт. Скрипт проверяет вердикт: «обязательно» должно опираться только на утверждения, выдержавшие возражения, ссылки должны вести на реальные реплики, а особое мнение каждой несогласной роли — сохраниться. Если независимого судью запустить нельзя, судит ведущий, и отчёт прямо говорит, что вердикт не независимый.
5. **Вердикт.** Решение и уверенность, что обязательно, желательно и не делаем, особые мнения и открытые вопросы. При ничьей решение остаётся за тобой.

**Размер спора можно задать в запросе, а можно не задавать:** «спорщиков: 5», «раундов: 2», «объём: коротко | обычно | подробно». Что не задано, агент выбирает сам по сложности темы и говорит, что выбрал: обычно 3–5 ролей, раунды до схождения позиций (не больше трёх), объём «обычно». Допустимо 2–10 ролей и 1–5 раундов. Объём задаёт, сколько каждая роль говорит за раунд: коротко — до 2 реплик по предложению, подробно — до 6 реплик и ответ на каждое возражение.

Все раунды и вердикт сохраняются в папке спора (`.debate/<тема>/`). Баллы — подсказка, а не доказательство. Спор ничего не меняет в коде и ничего не публикует. Тот же спор используют `close-threads` для спорных замечаний и `start-task` для спорных решений.

## check-bug

**Проверить баг**

Пример: `check-bug TASK-12`, несколько задач — `check-bug TASK-12 TASK-13`, или описание: `check-bug После перезапуска сбрасывается имя в профиле`.

Агент читает задачу Linear (без ключа — через MCP в Claude), выписывает шаги, ожидаемое и фактическое поведение и выясняет, как должно быть на самом деле: по условиям задачи, дизайну, коду или документации. Затем собирает приложение (версию из задачи, если она указана, иначе `main`), повторяет шаги на симуляторе и делает скриншот каждого шага. Шаг, где видна ошибка, отмечается.

Вердикт один из четырёх:

| Вердикт | Когда |
|---|---|
| Баг | Воспроизводится и отличается от задуманного; есть скриншот и источник ожидания |
| Не баг | Воспроизводится, но так и задумано; обязательно указано, где это записано |
| Не воспроизводится | Шаги выполнены, проблемы нет; перечислены все попытки |
| Нужны данные | Не хватает шагов, данных, версии, решения продукта или нет симулятора; перечислены вопросы |

Кроме самого бага агент выписывает бизнес-логику задачи отдельными правилами (кто и когда может это сделать, ограничения, что сохраняется, что показывается в каждом состоянии) и проверяет каждое в текущей мобилке — на симуляторе или по коду. На странице это блок «Бизнес-логика и мобилка»: «сходится 3 из 5 (60%)» и таблица «сходится / расходится / нет в мобилке / неясно» с источником и доказательством (шаг со скриншотом или место в коде). Непроверенное считается отдельно и не выдаётся за совпадение.

Отчёт — HTML-страница `.devloop/bugs/<номер>/report.html` со скриншотами внутри, ожидаемым и фактическим поведением, сборкой и устройством, вероятной причиной в коде и историей прошлых проверок. Сравнения «до/после» здесь нет: для проверки исправления используй `sim-verify-task`.

Навык не меняет код, статус и поля задачи. Комментарий в Linear с вердиктом и страницей — только по твоей просьбе. После вердикта «баг» можно запустить `start-task TASK-12`.

## match-design

**Сверить с дизайном**

Пример: приложи скриншот и напиши «Сверь с дизайном» или `match-design` — можно весь экран, можно кусок (карточку, кнопку, шапку). Если знаешь экран или состояние данных, назови их: «это профиль без питомцев».

Агент читает тексты на скриншоте, ищет экраны workbench (репозитория дизайна), в коде которых они есть, снимает 2–4 лучших кандидата в том же размере и плотности, что и скриншот, и находит, где на экране дизайна стоит твой скриншот или его фрагмент. Затем сравнивает попиксельно и глазами: тексты, цвета, шрифты, отступы, иконки, чего не хватает и что лишнее, отличаются ли только данные.

Ещё агент сверяет бизнес-логику экрана: читает код экрана в workbench (что показывается при каких данных, что доступно и когда, ограничения, куда ведут действия), находит тот же экран в мобильном коде и проверяет каждое правило. Результат — «сходится 4 из 6» и таблица правил с доказательствами (место в коде мобилки или «видно на скриншоте»).

Страница сравнения открывается в браузере: **Рядом**, **Наложение** с ползунком, **Отличия** с красной картой и рамками, таблица отличий с важностью и другие кандидаты. Небольшой процент отличающихся пикселей нормален — устройство и браузер по-разному сглаживают шрифты; вывод делает агент по списку отличий.

Нужен настроенный репозиторий дизайна в полном режиме (как для `filter-design`), Node.js 22+ и Google Chrome. В облегчённом режиме сравнение не выполняется. Навык только читает: ничего не меняет ни в дизайне, ни в мобилке, ни в Linear. Новые макеты и задачи по ним — это `filter-design`.

## help

**Помощь по Dev Loop**

Показывает это руководство и помогает выбрать навык. Можно попросить общий обзор, подробный разбор одного действия или объяснение непонятного статуса.

Примеры: «help — как начать?»; «Объясни разницу между sim-verify-task и close-threads»; «Что делает кнопка Create Linear tasks?»; «Почему задача остановилась?».

Справка не требует настроенного проекта, доступа к GitHub или устройства. Чтение справки не запускает проверки и ничего не публикует.

## requirements

**Что нужно настроить**

Для чтения справки в чате достаточно установленного плагина. Терминальная справка использует только Python 3.10+.

Для работы с проектами нужна локальная среда macOS или Linux, Git и Python 3.10+. Для сравнения изображений установи зависимости из `requirements.txt` в отдельное окружение. Текущие вспомогательные скрипты не поддерживают Windows напрямую.

| Сценарий | Дополнительно нужно |
|---|---|
| Проверка iOS | macOS, Xcode, запущенный Simulator; для точных нажатий — idb |
| Проверка Android | Android SDK, adb и запущенный эмулятор |
| Работа с GitHub | GitHub CLI (`gh`) с выполненным входом и доступом к проекту |
| Независимое ревью | Настроенный отдельный проверяющий, например Codex CLI |
| Работа с макетами | Node.js 22+, Google Chrome и доступ к репозиторию дизайна |
| Автоматическая подготовка плана макетов | Настроенный Claude CLI или Codex CLI; возможен расход квоты или оплата вызовов |
| Чтение и создание задач Linear | API-ключ, если уже есть; иначе плагин пробует MCP Linear в Claude и предлагает вход через браузер |

При первой работе с макетами агент уточнит репозиторий команды и предложит режим:

- **Полный:** скачивает проект дизайна и его зависимости. Можно получать текущие экраны и переносить макеты в код проекта дизайна.
- **Облегчённый:** скачивает тему, список экранов и правила задач. Текущие экраны не запускаются, а перенос макетов в код проекта дизайна недоступен. Данные мобильного проекта читаются через GitHub, если есть доступ.

При отсутствии ключа Linear используется официальный MCP: плагин ищет уже настроенное подключение Claude Code, при необходимости добавляет сервер только для текущего проекта и предлагает завершить вход через `/mcp`. Регистрация сервера ещё не означает, что вход выполнен. После входа агент проверяет доступ чтением задачи. Пароли и ключи в чат вводить не нужно. Подробнее: [подключение Linear](../../filter-design/references/linear-connection.md).

Выбор репозиториев сохраняется в `~/.handoff.json`. Повторно вводить его для каждой задачи не требуется. Ключи и пароли вводятся средствами соответствующего сервиса, а не в тексте чата.

## buttons

**Что делают кнопки на страницах**

В разных версиях страницы подписи могут оставаться на английском.

| Кнопка | Действие |
|---|---|
| Take / Взять | Включить этот вариант макета в выбранные |
| Rework / Доработать | Передать агенту комментарий, что изменить |
| Skip / Пропустить | Оставить этот макет вне текущего выбора |
| Linear: найденная задача / a new task | Выбрать, куда идёт задача: в уже существующую задачу Linear (макеты добавятся комментарием) или в новую |
| Create Linear tasks | Запросить создание задач по выбранным вариантам (или добавление в выбранные существующие) |
| Push to design | Запросить то же, что Create Linear tasks, и перенос каждого выбранного макета в репозиторий дизайна: отдельная ветка и PR, ссылка на PR появится в задаче. Статус задачи не меняется. Недоступна в облегчённом режиме и когда у экрана выбрано несколько вариантов |
| Download HTML | Скачать страницу выбранной задачи с изображениями |
| Open in Claude Artifact | Открыть уже сохранённый артефакт; если его нет, запросить создание через активную сессию Claude Code |
| Create Claude artifact | Запросить публикацию страницы макетов как артефакта Claude |
| Update Claude artifact | Запросить обновление существующего артефакта с сохранением ссылки |
| Dev Loop | Отправить комментарий и запустить работу: если задача ждёт ответа — продолжить с ответом; иначе пройти весь круг заново с учётом комментария |
| Full loop / Before / after only / Pull request and review | Что запускает Dev Loop: весь круг, только сравнение было / стало или PR с ревью |

Нажатие кнопки означает запрос, а успешная публикация подтверждается возвращённой ссылкой. Для кнопок локальной очереди нужна страница, открытая через работающий локальный сервер. Сохранённый HTML можно читать без него, но он не запускает агент самостоятельно.

Нативный артефакт Claude требует активной интерактивной сессии Claude Code с соответствующим инструментом. Обычная локальная страница работает без публикации артефакта. Обсуждение в артефакте и очередь локального отчёта — разные механизмы.

## storage

**Где сохраняется работа и как её продолжить**

Задачи разработки, отчёты, скриншоты и состояние очереди хранятся в `.devloop/` внутри целевого проекта. Эту папку не нужно включать в коммиты: в ней могут быть данные приложения и логи.

Проверки багов (`check-bug`) лежат отдельно, в `.devloop/bugs/<номер>/`, и не смешиваются с отчётами задач. Материалы макетов, рабочие копии и сессии сверки с дизайном (`match-design`, папка `match/`) находятся рядом с проектом дизайна в скрытой папке `.<имя-проекта>-handoff/`. Настройка репозиториев хранится отдельно в `~/.handoff.json`. Новые названия навыков не меняют эти пути.

Чтобы продолжить, открой исходный проект и напиши: «Продолжи задачу APP-42» или «Продолжи подготовку этих макетов». Агент сначала проверит сохранённое состояние. После прерывания он выяснит, что уже было сделано, прежде чем повторять отправку или другой шаг.

Для каждой задачи разработки сохраняется отдельный `report.html`. Его можно открыть после остановки сервера. При повторной проверке та же страница обновляется. Ссылка localhost работает только на том компьютере, где запущен сервер; для коллег нужен переданный HTML или опубликованный артефакт.

## troubleshooting

**Частые вопросы и остановки**

- **«Не проверено» или «частично».** Не хватило устройства, доступа, данных или выполненных шагов. Это не успешная проверка. В отчёте указано, что нужно добавить.
- **Кнопка нажата, но работа не продолжается.** Убедись, что сервер страницы и агент ещё работают, или напиши в исходном чате «Продолжи по запросу со страницы».
- **Страница localhost перестала открываться.** Сервер завершился или истекло время ожидания. Попроси открыть отчёт снова. Сохранённый HTML остаётся доступен.
- **Нет снимка текущего экрана.** Возможно, выбран облегчённый режим или текущий экран не удалось собрать. Для реального сравнения нужна полная настройка и рабочая сборка.
- **Нет ключа Linear.** Плагин сначала пробует подключение MCP в Claude. Заверши вход через `/mcp`, если он запрошен; подготовленные задачи и номера для проверки сохраняются. Подключение в Claude не даёт его инструменты сессии другого приложения автоматически.
- **Linear сообщает, что отправка уже выполняется.** Дождись её окончания. После аварийного завершения агент проверяет процесс и уже созданные задачи перед восстановлением. Самостоятельно удалять файлы состояния не нужно.
- **Решение по макетам устарело.** Макеты, изображения или проверки изменились. Нужно перестроить страницу и подтвердить выбор на новой версии.
- **Нет независимого проверяющего.** Нужно настроить доступного проверяющего или оставить этот этап незавершённым. Повторный просмотр тем же агентом не выдаётся за независимый.
- **Достигнут предел исправлений.** Агент покажет нерешённую причину. Новая постановка задачи получает отдельную историю вместо скрытого сброса старой.

## commands

**Справка из терминала**

В обычной работе достаточно чата. Команды ниже полезны, если нужно открыть руководство вручную или посмотреть аргументы скрипта.

Укажи путь к папке установленного плагина:

```bash
PLUGIN_DIR=/absolute/path/to/dev-loop
python3 "$PLUGIN_DIR/skills/help/scripts/help.py"
python3 "$PLUGIN_DIR/skills/help/scripts/help.py" --list
python3 "$PLUGIN_DIR/skills/help/scripts/help.py" filter-design
python3 "$PLUGIN_DIR/skills/help/scripts/help.py" troubleshooting
```

Первая команда выводит полное руководство, вторая — темы, остальные — выбранный раздел. Неверная тема возвращает ошибку со списком доступных разделов.

Вспомогательные программы имеют собственную справку:

```bash
python3 "$PLUGIN_DIR/skills/start-task/scripts/devloop.py" help
python3 "$PLUGIN_DIR/skills/start-task/scripts/devloop.py" --help
python3 "$PLUGIN_DIR/skills/start-task/scripts/devloop.py" enqueue --help
node "$PLUGIN_DIR/skills/filter-design/scripts/designs.mjs" --help
node "$PLUGIN_DIR/skills/filter-design/scripts/check.mjs" --help
node "$PLUGIN_DIR/skills/filter-design/scripts/handoff.mjs" --help
node "$PLUGIN_DIR/skills/filter-design/scripts/setup.mjs" --help
node "$PLUGIN_DIR/skills/filter-design/scripts/setup.mjs" linear --target /absolute/path/to/app-project
node "$PLUGIN_DIR/skills/filter-design/scripts/tasks.mjs" show T-10 T-11 --root /absolute/path/to/app-project
node "$PLUGIN_DIR/skills/match-design/scripts/match.mjs" --help
python3 "$PLUGIN_DIR/skills/check-bug/scripts/build_bug_report.py" --help
bash "$PLUGIN_DIR/skills/sim-verify-task/scripts/sim.sh" --help
```

`help` показывает руководство плагина, а `--help` — параметры конкретной программы. Подкоманды вспомогательных скриптов остаются техническими: например, `enqueue` ставит задачу в очередь, `status` показывает состояние, а `linear` отправляет подготовленный план в Linear. Агент выбирает их сам; запоминать их для работы в чате не нужно.

## migration

**Какие названия изменились**

| Старое название навыка | Новая команда | Название в меню |
|---|---|---|
| `dev-loop`, `implement-task` | `start-task` | Выполнить задачу |
| `sim-verify`, `check-app`, `check-task` | `sim-verify-task` | Проверить задачу до и после |
| `pr-review-loop`, `review-task`, `review-pr`, `discuss-review` | `close-threads` | Закрыть все треды |
| `agent-council` | `debate` | Спор |
| `handoff`, `handoff-check`, `handoff-push`, `design-to-tasks`, `check-design`, `update-design` | `filter-design` | Фильтр дизайна |
| `bug-check`, `is-it-a-bug` | `check-bug` | Проверить баг |
| `compare-design`, `design-match` | `match-design` | Сверить с дизайном |
| — | `help` | Помощь по Dev Loop |

Имя самого плагина остаётся `dev-loop`. Старые имена принимаются как темы терминальной справки: например, `help.py handoff` открывает раздел `filter-design`. Для вызова навыков используй новые команды. Если в своих скриптах ты указал полный путь через старую папку навыка, замени его по таблице. Существующие задачи, настройки, ветки и сохранённые страницы не переименовываются.
